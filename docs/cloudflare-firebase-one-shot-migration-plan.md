# خطة تصميم وتنفيذ الترحيل الكامل لمتجر Baak Books

## 1. القرار المعتمد

سيُبنى نظام Cloudflare Pages + Firebase كاملًا ويُختبر قبل لمس البيانات الحية. بعد اعتماد الجاهزية، سيتم نقل بيانات PythonAnywhere إلى Firebase **مرة واحدة في نافذة قطع واحدة**، ثم تحويل المتجر إلى النسخة الجديدة.

لن نستخدم ترحيلًا تدريجيًا للطلبات، ولن نشغّل مزامنة مستمرة بين النظامين، ولن نقسم الانتقال إلى تشغيل إنتاجي مزدوج. بدل ذلك سنستخدم بيئة تجريبية ببيانات اصطناعية أو نسخة منقّحة لا تحتوي بيانات العملاء، ثم نُجري النقل الحي النهائي بعد مضاعفة الحساب والفحص.

> **القاعدة غير القابلة للتجاوز:** لا `git push`، ولا إنشاء/تعديل إنتاج Cloudflare أو Firebase، ولا تغيير DNS، ولا تصدير أو تعديل PythonAnywhere، ولا استيراد بيانات حية، قبل موافقة المستخدم الصريحة على المرحلة التي تتطلب ذلك.

## 2. افتراضات يجب تثبيتها

سأبني الخطة على الافتراضات التالية، ويمكن تعديلها قبل التنفيذ:

| القرار | الافتراض الحالي |
|---|---|
| قاعدة Firebase | Cloud Firestore وليس Realtime Database |
| الصور | الإبقاء على روابط ImgBB الحالية في النقل الأول، ثم إضافة مكتبة الصور لاحقًا |
| الواجهة | تطبيق ثابت مستقل من Flask، مستضاف على Cloudflare Pages |
| العمليات الحساسة | Firebase Cloud Functions 2nd gen باستخدام TypeScript، وليست من المتصفح مباشرة |
| الإدارة | Firebase Authentication مع دور `admin` بدلاً من `ADMIN_TOKEN` |
| عنوان الموقع | اعتماد `https://baakbook.pages.dev` كعنوان الإنتاج؛ لا نحتاج إلى تغيير DNS لدومين مخصص في مرحلة القطع |
| الدفع | الإبقاء على الدفع عند الاستلام كما هو حاليًا |
| الترحيل الحي | تصدير نهائي واحد من PythonAnywhere ثم استيراد نهائي واحد إلى Firebase |
| الرجوع | الاحتفاظ بالنسخة القديمة كاملة حتى انتهاء فترة احتفاظ يحددها المستخدم، والتراجع عبر إعادة عنوان الموقع القديم إن كان هناك دومين مخصص |

ملاحظة مهمة: عنوان `pythonanywhere.com` الفرعي لا يمكن نقله إلى Cloudflare Pages. إذا لم يملك المتجر دومينًا مخصصًا فسيكون العنوان الجديد `*.pages.dev` أو دومينًا يختاره المستخدم.

## 3. التصميم المستهدف

### 3.1 البنية العامة

```text
الزائر / المدير
        |
        v
Cloudflare Pages
(واجهة المتجر واللوحة)
        |
        +--> Firebase Authentication
        |
        +--> Firestore للقراءة العامة الآمنة
        |
        +--> HTTPS Callable Functions
               |
               +--> التحقق من المنتجات والأسعار والتوفر
               +--> إنشاء الطلبات بشكل idempotent
               +--> ImgBB عبر مفتاح سري
               +--> صلاحيات الإدارة والتدقيق
```

Cloudflare Pages مسؤول عن الملفات الثابتة والمعاينات والنشر. لا يحتوي على مفتاح Firebase Admin ولا مفتاح ImgBB. Firestore يحفظ البيانات، بينما Cloud Functions تنفذ العمليات التي لا يجوز الوثوق فيها بالمتصفح، مثل تثبيت السعر النهائي وإنشاء الطلب وتعديل المخزون.

### 3.2 مكونات المستودع الجديد

سنفصل التطبيق إلى أجزاء واضحة داخل المستودع المحلي:

```text
baakbook/
├── frontend/                 # تطبيق Cloudflare Pages
│   ├── src/
│   │   ├── catalog/          # المنتجات والتصفية والبحث
│   │   ├── cart/             # السلة وخلط الشخصي بالهدية
│   │   ├── discovery/        # اكتشف كتابك والاقتراحات المبررة
│   │   ├── gifts/             # هدية كتاب، هدية مجموعة، البحث عن هدية
│   │   ├── admin/             # لوحة الإدارة والمكتبة
│   │   ├── firebase/          # تهيئة Firebase العامة فقط
│   │   └── shared/            # التنسيق، الأخطاء، التحقق المشترك
│   ├── index.html
│   └── package.json
├── functions/                # Firebase Cloud Functions
│   ├── src/
│   │   ├── orders/            # إنشاء الطلب والتحقق وإعادة الحساب
│   │   ├── products/          # عمليات الإدارة والتحقق من التوفر
│   │   ├── images/            # ImgBB ومكتبة الصور
│   │   ├── admin/             # أدوار المدير والتدقيق
│   │   └── migration/         # أدوات التحقق والاستيراد، لا تُستدعى من الواجهة
│   ├── package.json
│   └── firestore.rules
├── migration/
│   ├── source-schema.json
│   ├── transform.ts
│   ├── verify-source.ts
│   ├── verify-target.ts
│   ├── reconciliation.ts
│   └── README.md
├── firestore.indexes.json
├── firebase.json
├── README.md
└── docs/
    ├── architecture.md
    ├── data-contract.md
    ├── cutover-runbook.md
    └── rollback-runbook.md
```

لن نُبقي Flask كجزء من المسار الإنتاجي الجديد، لكن سنحتفظ به في فرع أو مجلد تاريخي حتى تظل عملية الرجوع ممكنة.

## 4. مخطط Firestore المقترح

### 4.1 المجموعات

| المجموعة | الغرض | سياسة الوصول |
|---|---|---|
| `products` | الكتب المنشورة وبياناتها | قراءة عامة للحقول المنشورة؛ كتابة للمدير عبر Functions |
| `categories` | التصنيفات | قراءة عامة؛ كتابة للمدير |
| `deliveryFees` | رسوم التوصيل | قراءة عامة؛ كتابة للمدير |
| `settings/public` | أعلام الميزات وإعدادات العرض | قراءة عامة لحقول العرض؛ كتابة للمدير |
| `orders` | الطلبات القديمة والجديدة | لا قراءة عامة؛ المدير عبر Function أو وصول مقيد |
| `imageLibrary` | روابط ImgBB وبيانات الصور | المدير فقط |
| `auditLogs` | سجل تعديل المنتجات والطلبات والإعدادات | المدير فقط، دون حذف من الواجهة |
| `migrationMetadata` | دفعات النقل والبصمات والتقارير | أداة الترحيل والمدير فقط |

### 4.2 عقد المنتج

يُحافظ على الحقول الحالية المتوافقة مع منطق Baak Books:

```json
{
  "id": "bk001",
  "title": "قواعد جارتين",
  "category": "روايات",
  "desc": "وصف تحريري قصير",
  "img": "https://...",
  "price": 1200,
  "availability_type": "in_stock",
  "stock_quantity": 10,
  "lead_time_min_days": 0,
  "lead_time_max_days": 0,
  "active": true,
  "featured": false,
  "giftable": true,
  "discoverable": true,
  "discovery_tags": ["story", "mystery"],
  "gift_tags": ["warm"],
  "legacyId": "bk001",
  "schemaVersion": 1,
  "updatedAt": "server timestamp"
}
```

القواعد غير القابلة للتغيير في الترحيل:

- `availability_type` لا يتجاوز `in_stock` و`on_demand`.
- مدة الاقتناء لا تتجاوز 0 أو 1 يومًا.
- المنتج غير النشط لا يظهر ولا يقبل طلبًا جديدًا.
- المنتج حسب الطلب يظهر مدته بوضوح.
- لا يُنقل السعر من المتصفح كحقيقة نهائية؛ السعر يثبت من وثيقة المنتج الموثوقة عند إنشاء الطلب.

### 4.3 عقد الطلب

يُحفظ الطلب الجديد والقديم معًا، مع نسخة تاريخية من عناصره حتى لا تتغير قيمة الطلب إذا تغير المنتج لاحقًا:

```json
{
  "id": "order-123",
  "legacyOrderId": 123,
  "status": "new",
  "items": [
    {
      "productId": "bk001",
      "titleSnapshot": "قواعد جارتين",
      "unitPriceSnapshot": 1200,
      "quantity": 1,
      "purchase_purpose": "gift",
      "gift_group_id": "gift-1",
      "availabilitySnapshot": "in_stock"
    }
  ],
  "giftGroups": [
    {
      "id": "gift-1",
      "recipientName": "...",
      "recipientPhone": "...",
      "message": "..."
    }
  ],
  "customer": {},
  "delivery": {},
  "subtotal": 1200,
  "deliveryFee": 850,
  "total": 2050,
  "idempotencyKey": "...",
  "source": "legacy-pythonanywhere",
  "createdAt": "timestamp",
  "schemaVersion": 1
}
```

لن نحذف أو نعيد تفسير الطلبات القديمة. إذا كانت بعض الحقول القديمة مختلفة، نحتفظ بالحمولة الأصلية داخل `legacyPayload` مقيدة الوصول، ونضع الحقول الجديدة كإسقاط موثق.

## 5. الأمن والعمليات الحساسة

### 5.1 المصادقة والصلاحيات

- المدير يسجل الدخول عبر Firebase Authentication.
- يمنح حساب المدير claim باسم `admin` بعد تحقق يدوي.
- لا توجد صلاحيات إدارية اعتمادًا على قيمة مخفية في HTML أو JavaScript.
- قواعد Firestore تمنع الزوار من القراءة أو الكتابة إلى `orders` و`auditLogs` و`imageLibrary`.
- المنتجات العامة لا تُعرض إلا إذا كانت `active`، مع منع العميل من تغيير السعر أو التوفر.

### 5.2 إنشاء الطلب

المتصفح يرسل محتويات السلة وبيانات العميل والهدية إلى Function موثوقة. Function تعيد قراءة المنتجات من Firestore، وتتحقق من:

- وجود المنتج ونشاطه.
- السعر الحالي.
- الكمية والتوفر.
- السماح بالإهداء لكل منتج.
- مستلم واحد ومجموعة هدية واحدة.
- رقم هاتف المستلم.
- مدة الكتب التي يمكن اقتناؤها.
- رسوم التوصيل والحساب النهائي.

يُرسل كل طلب مع `idempotencyKey`، ويعيد نفس نتيجة الطلب بدل إنشاء طلب مكرر عند إعادة المحاولة. تُسجل الأخطاء برسالة آمنة للعميل ومعرف تتبع داخلي.

### 5.3 الصور وImgBB

يبقى مفتاح ImgBB سرًا داخل Cloud Functions. ترفع لوحة الإدارة الصورة إلى Function، وتتحقق Function من النوع والحجم، ثم تحفظ الرابط والبيانات الوصفية في `imageLibrary`. لا يصل مفتاح ImgBB إلى المتصفح، وتبقى خانة إدخال الرابط اليدوي متاحة مؤقتًا للكتب الحالية.

## 6. استراتيجية التحقق المزدوج

لأن المستخدم طلب الحساب والفحص مرتين، سننفذ مسارين مستقلين لا يعتمدان على نفس دالة التحويل وحدها.

### الفحص الأول: تحقق المصدر والتحويل

أداة مستقلة تقرأ نسخة JSON وتنتج:

- عدد كل نوع من السجلات.
- قائمة المعرفات وترتيبها.
- مجموع الطلبات ومجموع عناصر الطلبات.
- مجموع القيم المالية للطلب قبل وبعد التحويل.
- كشف التكرارات والحقول المفقودة والقيم غير الصالحة.
- بصمة SHA-256 لكل سجل بعد ترتيب حقوله بشكل حتمي.
- تقرير روابط الصور المفقودة أو غير الصالحة.

### الفحص الثاني: تحقق الهدف وإعادة البناء

أداة ثانية تقرأ Firestore بعد الاستيراد، وتعيد حساب الإحصاءات من الوثائق المخزنة دون استعمال تقرير المصدر. ثم تقارن:

| المقياس | المصدر | الهدف | شرط النجاح |
|---|---:|---:|---|
| المنتجات | محسوب مستقلًا | محسوب مستقلًا | تطابق كامل |
| التصنيفات | محسوب مستقلًا | محسوب مستقلًا | تطابق كامل |
| رسوم التوصيل | محسوب مستقلًا | محسوب مستقلًا | تطابق كامل |
| الطلبات | محسوب مستقلًا | محسوب مستقلًا | تطابق كامل |
| إجمالي عناصر الطلبات | محسوب مستقلًا | محسوب مستقلًا | تطابق كامل |
| مجموع المبالغ التاريخية | محسوب مستقلًا | محسوب مستقلًا | تطابق كامل أو فرق موثق |
| بصمات المعرفات | مجموعة المصدر | مجموعة الهدف | لا فقد ولا تكرار |

بعد ذلك تُجرى مقارنة ثالثة على عينات مقصودة: كتاب متوفر، كتاب غير متوفر، كتاب يمكن اقتناؤه، كتاب قابل للإهداء، طلب شخصي، طلب هدية، طلب مختلط، وطلب بحالة قديمة.

لا يُسمح بالقطع إذا ظهر فرق غير مفسر، حتى لو كان الفرق في سجل واحد.

## 7. مراحل التنفيذ بعد اعتماد الخطة

### المرحلة A — بناء التصميم محليًا

ننشئ طبقة الواجهة الجديدة وCloud Functions ومخطط Firestore وأدوات التحقق داخل بيئة محلية منفصلة. نستخدم بيانات اصطناعية أو نسخة منقحة فقط. لا نرفع أي شيء إلى GitHub، ولا ننشئ مشروع Firebase إنتاجيًا، ولا نربط Cloudflare بالدومين.

### المرحلة B — بيئة Staging كاملة

بعد موافقة منفصلة، ننشئ مشروع Firebase Staging ونختبر فيه القواعد والوظائف والواجهة. يمكن استخدام نسخة غير حساسة من البيانات للتحقق من التكافؤ الوظيفي. لا نستخدم بيانات العملاء الحقيقية في Staging إلا إذا وافق المستخدم صراحة وبطريقة آمنة.

### المرحلة C — بوابة الجاهزية

ننفذ قائمة قبول كاملة:

- بناء Cloudflare Pages بنجاح.
- تسجيل دخول المدير.
- قراءة الكتالوج والتصنيفات ورسوم التوصيل.
- البحث والاكتشاف والهدايا والسلة.
- إنشاء طلب تجريبي مع إعادة حساب السعر في Function.
- منع تكرار الطلب.
- منع الوصول الإداري غير المصرح.
- اختبار كتب يمكن اقتناؤها بمدة اليوم نفسه ويوم واحد.
- اختبار ImgBB أو إبقاؤه معطلًا إذا لم نبدأ به.
- نجاح الفحصين المستقلين.
- وجود نسخة رجوع كاملة.

إذا فشل عنصر واحد، لا ننتقل إلى النقل الحي.

### المرحلة D — النقل الحي الواحد

قبل القطع، نختار نافذة قصيرة ونبلغ المستخدم بها. الترتيب الدقيق:

1. نوقف التعديلات الإدارية والطلبات الجديدة مؤقتًا على PythonAnywhere.
2. نأخذ نسخة نهائية من `data.json` الحي مع وقت وبصمة SHA-256.
3. نشغل فحص المصدر الأول.
4. ننفذ تحويلًا نهائيًا إلى Firestore مرة واحدة بمعرف دفعة فريد.
5. نشغل فحص الهدف الثاني وإعادة الحساب.
6. نشغل مقارنة البصمات والعدادات والقيم المالية والعينات.
7. إذا لم توجد فروقات غير مفسرة، نفعل الإنتاج الجديد.
8. نجعل `https://baakbook.pages.dev` عنوان الإنتاج مرة واحدة، بعد التأكد من نجاح النشر والاختبارات.
9. ننفذ طلبًا تجريبيًا محدودًا من الموقع الجديد.
10. نعيد فتح استقبال الطلبات.
11. نحتفظ بالنسخة القديمة دون حذف.

إذا فشل أي فحص قبل تغيير العنوان، نوقف العملية ونعود دون تغيير الموقع. إذا فشل بعد تغيير العنوان، نستخدم Runbook الرجوع ونبقي تقرير الفرق والطلب التجريبي محفوظين.

## 8. خطة الرجوع

- عند وجود خلل في الواجهة قبل الطلبات: نعيد العنوان إلى PythonAnywhere.
- عند وجود خلل في إنشاء الطلبات: نوقف الطلبات الجديدة، نعيد العنوان القديم، ونحفظ أي طلبات وصلت إلى Firebase لمنع تكرارها عند المعالجة.
- لا نمسح Firestore ولا نعيد تصديره بشكل أعمى.
- لا نحذف PythonAnywhere أو `data.json` أو نسخة المصدر.
- لا نعتبر الانتقال ناجحًا نهائيًا إلا بعد فترة مراقبة يحددها المستخدم، والتوصية 30 يومًا.

## 9. ما يلزم من المستخدم عند بدء التنفيذ

1. تأكيد اعتماد **Cloud Firestore** بدل Realtime Database.
2. اعتماد `https://baakbook.pages.dev` عنوان الإنتاج في هذه المرحلة؛ لا يلزم دومين مخصص أو تغيير DNS.
3. تحديد اسم مشروع Firebase أو السماح باقتراح اسم.
4. تأكيد أن القطع النهائي سيحتاج نافذة قصيرة لا تُقبل فيها طلبات جديدة.
5. عند الوصول للمرحلة الحية: تنفيذ أو تأكيد تصدير `data.json` من حساب PythonAnywhere.
6. الموافقة الصريحة المنفصلة على أي `git push` أو إنشاء مشروع إنتاجي أو تغيير DNS.
