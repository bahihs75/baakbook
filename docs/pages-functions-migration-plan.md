# خطة إعادة هيكلة API إلى Cloudflare Pages Functions

## الغرض

هذه الوثيقة تسجل نتيجة مراجعة الطبقات الموجودة قبل أي إعادة هيكلة كبيرة. الهدف هو تشغيل واجهة Baak Books من Cloudflare Pages بعنوان `baakbook.pages.dev` مع الحفاظ على عقود الواجهة الحالية، واستخدام مشروع Firebase الصحيح `baakbook-77c00`، دون تعديل PythonAnywhere أو البيانات الحية أو تنفيذ `git push`.

## النتيجة الأساسية

لا يمكن نقل `cloudflare/worker/src/index.ts` إلى Pages Functions كما هو. الملف الحالي مصمم لبيئة Cloudflare Worker مستقلة ويعتمد على D1 وR2 و`ADMIN_TOKEN`. أما قرار Firestore الحالي فيضع العمليات الحساسة في Firebase Functions، ويوجد بالفعل منطق موثوق لإنشاء الطلب داخل `functions/src/index.ts` باستخدام معاملة Firestore و`orderIdempotency`.

نسخ Worker حرفيًا سيخلق طبقة ثانية تحسب المخزون والأسعار، وهذا يفتح احتمال اختلاف النتائج بين D1 وFirestore. لذلك سيكون النقل على مرحلتين داخل النسخة المحلية، مع عدم تغيير سلوك الموقع المنشور:

1. **Pages Functions** تصبح طبقة HTTP متوافقة مع مسارات الواجهة الحالية، وتتعامل مع القراءة العامة والتنسيق والربط.
2. **Firebase Functions** تبقى حد الثقة للعمليات الحساسة: إنشاء الطلب، التحقق من السعر والمخزون، تحديثات الإدارة، وسجل التدقيق.
3. **Firestore** هو المصدر الوحيد للبيانات بعد الاستيراد؛ لا يبقى D1 جزءًا من مسار الإنتاج.
4. **Firebase Authentication** يستبدل رمز الإدارة اليدوي بعد إضافة تحقق ID token وامتياز المدير.

## عقود الواجهة الحالية

| المسار | الطريقة | المستهلك | القرار في النسخة الجديدة |
|---|---:|---|---|
| `/api/products` | GET | المتجر ولوحة الإدارة | Pages Function للقراءة العامة/الإدارية بعد تطبيق حدود واضحة |
| `/api/products/:id` | GET | المتجر | Pages Function لعرض كتاب واحد |
| `/api/categories` | GET | المتجر | Pages Function للقراءة العامة |
| `/api/delivery-fees` | GET | المتجر | Pages Function للقراءة العامة المحدودة |
| `/api/settings` | GET | المتجر | Pages Function لقراءة الإعدادات العامة فقط |
| `/api/discover` | POST | المتجر | Pages Function لتوصيات القراءة بعد قراءة الكتالوج العام |
| `/api/orders` | POST | المتجر | Pages Function متوافقة تستدعي حد الثقة في Firebase؛ لا تعيد حسابًا محليًا مستقلًا |
| `/api/admin/*` | GET/POST/PUT/DELETE | لوحة الإدارة | Pages Functions تتحقق من Firebase ID token وتفوض الكتابة إلى Firebase Functions أو طبقة موثوقة |
| `/api/admin/upload-image` | POST | مكتبة الإدارة | يؤجل إلى مسار موثوق؛ ImgBB/R2 لا يضاف قبل تثبيت الأسرار وسياسة التخزين |

## قواعد التوافق

تحافظ النسخة الجديدة على الحقول التي تعتمد عليها الواجهة، بما فيها `id`, `title`, `author`, `desc`, `price`, `stock_quantity`, `availability_type`, `lead_time_days`, `img`, `category`, `giftable`, `discoverable`, و`featured`. ويمكن تخزين الحقول التاريخية داخل `legacyPayload` لأغراض التحقق والرجوع، لكن لا تستخدم الواجهة قيمة السعر أو المخزون المرسلة من العميل عند إنشاء الطلب.

يستمر مفتاح `Idempotency-Key` في طلبات إنشاء الطلب. يعاد الطلب السابق عند تكرار المفتاح بدل إنشاء طلب ثانٍ. وتبقى قاعدة الإصدار الأول: مستلم واحد ومجموعة هدية واحدة لكل طلب، مع إلزام هاتف المستلم عند وجود هدية، ومدة الكتب المقتناة لا تتجاوز اليوم نفسه أو يومًا واحدًا.

## قرارات أمان لا يجوز تجاوزها

> إعداد Firebase Web App Config ليس سرًا، لكنه لا يمنح صلاحية الكتابة. قواعد Firestore والتحقق من Firebase ID token وحدود الخادم هي الحماية الفعلية.

لا يوضع Firebase Admin credential أو service-account JSON أو ImgBB API key في `frontend/` أو في GitHub. أي اعتماد خادمي مطلوب لطبقة موثوقة يحفظ في أسرار Firebase أو Cloudflare بعد أن ينشئه المستخدم ويوافق عليه. لا تستخدم Pages Function قيمة `ADMIN_TOKEN` القديمة في الإنتاج.

## خطوات التنفيذ المقترحة بعد الموافقة

1. إنشاء adapter مشترك لقراءة Firestore مع بيئة Emulator أولًا، بدل نسخ استعلامات D1.
2. إنشاء ملفات Pages Functions محددة للمسارات العامة، مع موجه أخطاء موحد و`requestId`.
3. توسيع Firebase Functions لتقديم نقاط HTTP أو callable مطابقة لإنشاء الطلب وتحديثات الإدارة، مع اختبارات وحدات للحمولات الحالية.
4. تعديل الواجهة تدريجيًا إلى Firebase Auth في لوحة الإدارة، مع إبقاء `API_BASE` قابلاً للتبديل محليًا.
5. تشغيل الاختبارات على بيانات صناعية/Emulator فقط، ثم إجراء فحص تكافؤ مستقل قبل التفكير في الاستيراد.

## ما لم يُنفذ في هذه المرحلة

لم تُنشأ ملفات Pages Functions بعد، ولم تُنشر Firebase Rules أو Firebase Functions، ولم يُستورد أي سجل إلى المشروع الحقيقي، ولم يُنشأ مشروع Cloudflare Pages، ولم يُعدّل GitHub أو PythonAnywhere.

## بوابة الموافقة

إنشاء ملفات Functions وتغيير عقود المصادقة يُعد تغييرًا معماريًا كبيرًا. يلزم تأكيد المستخدم قبل البدء به، مع اعتماد القرار التالي صراحةً:

**Pages Functions طبقة HTTP متوافقة، وFirebase Functions حد الثقة للطلبات وتعديلات الإدارة، وFirestore مصدر البيانات الوحيد بعد الترحيل.**
