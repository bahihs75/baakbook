# خطة ترحيل Baak Books من PythonAnywhere إلى Cloudflare Pages + Firebase

## 1. الهدف

نقل Baak Books تدريجيًا من تطبيق Flask المستضاف على PythonAnywhere وملف `data.json` إلى واجهة مستقلة مستضافة على Cloudflare Pages، مع استخدام Firebase كطبقة البيانات الأساسية. يجب أن تتم العملية **دون فقد أي منتج أو طلب أو إعداد**، مع إبقاء الموقع الحالي يعمل حتى تنجح النسخة الجديدة ويوافق المستخدم صراحةً على التحويل النهائي.

> القاعدة الحاكمة: لا تعديل على PythonAnywhere، ولا تغيير في DNS، ولا استيراد إلى Firebase، ولا `git push`، ولا حذف لأي نسخة احتياطية قبل موافقة المستخدم على المرحلة المعنية.

## 2. القرار المعماري المقترح

سأتعامل مع عبارة «Firebase DB» على أنها **Cloud Firestore**، لأنه أنسب من Realtime Database لبيانات المنتجات والطلبات والإعدادات التي تحتاج إلى وثائق واضحة واستعلامات وفهارس وقواعد وصول. يمكن تغيير هذا القرار قبل بدء التنفيذ، لكن تغيير نوع قاعدة البيانات بعد بناء طبقة الترحيل سيزيد العمل والمخاطر.

البنية المستهدفة ستكون مفصولة إلى طبقات:

| الطبقة | التقنية | المسؤولية |
|---|---|---|
| الواجهة العامة | Cloudflare Pages | عرض المتجر، البحث، الاكتشاف، السلة، نماذج الهدايا، وتجربة الشراء |
| المصادقة | Firebase Authentication | دخول المدير فقط، بدل رمز الإدارة الثابت الحالي |
| البيانات | Cloud Firestore | المنتجات، التصنيفات، رسوم التوصيل، الطلبات، إعدادات الميزات، ومكتبة الصور إن اعتمدت |
| العمليات الحساسة | Firebase Cloud Functions أو نقطة خلفية موثوقة | إنشاء الطلب بعد التحقق من السعر والتوفر، منع العبث، وتطبيق idempotency |
| حماية البيانات | Firestore Security Rules + App Check عند الإمكان | منع القراءة والكتابة غير المصرح بها والتحقق من بنية البيانات |
| الصور | تبقى روابط ImgBB الحالية في المرحلة الأولى | لا ننقل الصور أو نغيّر مزودها أثناء ترحيل البيانات، لتقليل المخاطر |
| النشر | Cloudflare Pages متصل بمستودع GitHub | معاينات للفروع، ثم نشر الإنتاج بعد موافقة صريحة |

لن تُوضع مفاتيح Firebase الخاصة بالامتيازات أو مفاتيح ImgBB أو أي أسرار إدارية داخل الواجهة أو GitHub. إعدادات Firebase العامة الخاصة بتطبيق الويب ليست بديلًا عن قواعد Firestore أو صلاحيات الإدارة.

## 3. ما لن نفعله في البداية

لن نبدأ بإنشاء مشروع إنتاجي أو استيراد البيانات الحية مباشرة. ولن نعيد تصميم كل الميزات أثناء الترحيل. الأولوية هي نقل البيانات والحفاظ على التكافؤ الوظيفي للنسخة الحالية، ثم تحسينات منفصلة بعد استقرار النسخة الجديدة.

لن نستخدم Firestore من الواجهة لتسجيل السعر النهائي اعتمادًا على قيمة أرسلها المتصفح. سيعاد حساب الأسعار والتحقق من المنتجات والتوفر ومدة الاقتناء في طبقة موثوقة قبل إنشاء الطلب. هذا مهم لأن العميل يستطيع تعديل طلب HTTP حتى لو كانت الواجهة سليمة.

## 4. المراحل التنفيذية

### المرحلة 0 — تجميد النطاق وتوثيق القرار

نثبت أن الهدف هو Cloudflare Pages + Firestore، ونثبت أسماء البيئات التالية:

- `baak-books-staging`: بيئة Firebase تجريبية.
- مشروع Pages تجريبي أو Preview Deployments للنسخة الجديدة.
- بيئة الإنتاج الجديدة، ولا تُنشأ أو تُربط بالدومين إلا بعد اجتياز الاختبارات.

في هذه المرحلة نوثق أيضًا ما إذا كان الدومين الحالي سيبقى نفسه عند التحويل، وما إذا كان المستخدم يريد الاحتفاظ بـ ImgBB للصور. الافتراض الافتراضي هو إبقاء ImgBB كما هو وعدم ترحيل الصور في الجولة الأولى.

**مخرج المرحلة:** وثيقة قرارات قصيرة يوافق عليها المستخدم قبل لمس أي خدمة خارجية.

### المرحلة 1 — جرد البيانات دون تعديلها

نقرأ نسخة المشروع المحلي والنسخة التي يصدّرها المستخدم من PythonAnywhere، وننتج تقرير جرد يتضمن عدد المنتجات، التصنيفات، رسوم التوصيل، الطلبات، الإعدادات، أعلى وأدنى رقم طلب، والحقول القديمة أو الناقصة.

يجب الحصول على **تصدير من `data.json` الحي على PythonAnywhere** من المستخدم أو من جلسة PythonAnywhere التي يملكها. النسخة المحلية لا تُعتبر نسخة من بيانات العملاء الحقيقية، ولا يجوز استخدامها بدل التصدير الحي.

سننشئ نسخًا منفصلة للقراءة فقط، ونحسب SHA-256 لكل ملف تصدير، ونسجل وقت التصدير ومصدره. لا نضع التصدير الحي في GitHub أو داخل ملفات الواجهة.

**مخرج المرحلة:** `source-data-inventory.json` وتقرير فروقات يوضح ما سيُرحّل وما يحتاج قرارًا.

### المرحلة 2 — تصميم مخطط Firestore وخريطة التحويل

نحوّل النموذج الحالي إلى مجموعات Firestore واضحة مع معرفات مستقرة. المقترح:

| المجموعة | المحتوى الأساسي | ملاحظات |
|---|---|---|
| `products` | الكتب وحقول التوفر والسعر ووسوم الاكتشاف والإهداء | الحفاظ على `id` الحالي إن كان فريدًا، وإضافة `legacyId` عند الحاجة |
| `categories` | التصنيفات | يمكن أن تكون وثائق أو إعدادًا منظمًا؛ نختار الأبسط بعد الجرد |
| `deliveryFees` | رسوم الولايات أو المناطق | حفظ القيم السالبة أو غير المتاحة كحالات واضحة لا كرسوم صالحة |
| `orders` | الطلبات القديمة والجديدة | حفظ نسخة من بيانات الطلب الأصلية وحقول الحالة والتواريخ |
| `settings` | أعلام الميزات والإعدادات العامة | لا يكتبها إلا المدير |
| `imageLibrary` | روابط الصور وبياناتها | تُضاف في مرحلة ImgBB، ولا تكون شرطًا لترحيل المتجر |
| `migrationMetadata` | مصدر الترحيل وإصداره وتوقيعه ونتيجته | للمراجعة ومنع تشغيل الاستيراد مرتين بالخطأ |

نحافظ على منطق Baak Books الحالي، بما في ذلك:

- مسارات الإهداء الثلاثة، مع مستلم واحد ومجموعة هدية واحدة لكل طلب.
- السماح بالخلط بين المشتريات الشخصية والهدية ضمن القواعد المعتمدة.
- الكتب التي يمكن اقتناؤها في اليوم نفسه أو خلال يوم واحد فقط.
- أعلام الميزات: الاكتشاف، الهدايا، الهدايا من البطاقة والسلة، البحث عن هدية، الوضع الليلي، والميزات التجريبية.
- حالات الطلبات الحالية، مع توحيد القيم القديمة مثل `New` و`Processing` و`Delivered` دون حذف القيمة الأصلية.

لكل تحويل نكتب قاعدة صريحة، مثل تحويل `img` إلى `imageUrl` إن قررنا إعادة التسمية، أو الإبقاء على الاسم القديم لتقليل التغيير. لا نغيّر أسماء الحقول بلا خريطة تحويل قابلة للاختبار.

**مخرج المرحلة:** مخطط بيانات، خريطة تحويل، وقائمة حالات تحتاج قرار المستخدم.

### المرحلة 3 — بناء أدوات الترحيل الجافة

نبني سكربتًا محليًا لا يتصل بالإنتاج ولا يكتب إلى Firebase في وضع المعاينة. يقرأ نسخة JSON، يطبع تقرير التحقق، ويتحقق من:

- معرفات المنتجات الفريدة.
- الأسعار والكميات والأنواع المنطقية.
- أن `availability_type` محصور في `in_stock` و`on_demand`.
- أن مدة الاقتناء محصورة في `0` أو `1`.
- أن كل عنصر في الطلب يشير إلى منتج معروف أو يحمل بيانات تاريخية محفوظة.
- أن الطلبات لا تُكرر عند إعادة تشغيل الأداة.
- أن إجمالي الطلبات والمنتجات بعد التحويل يساوي المصدر.

يجب أن يكون الاستيراد **idempotent**، أي أن تشغيله مرتين لا ينشئ طلبات أو منتجات مكررة. نستخدم معرفات ثابتة، ونسجل `migrationBatchId` و`sourceHash`.

**مخرج المرحلة:** أداة تحويل واختبارات لها، مع تقرير Dry Run لا يكتب إلى Firebase.

### المرحلة 4 — إنشاء بيئة Firebase التجريبية

بعد موافقة المستخدم، ننشئ مشروع Firebase تجريبيًا منفصلًا، ونفعل Firestore وAuthentication، ونجهز قواعد Firestore في وضع مقيد. لا نستخدم مشروع الإنتاج لهذه الخطوة.

نضيف حساب مدير تجريبيًا ونمنحه صلاحية إدارية محددة، ونجعل القراءة العامة مقتصرة على المنتجات والإعدادات التي يحتاجها المتجر. الطلبات لا تكون قابلة للقراءة العامة، والكتابة الحساسة تمر عبر عملية موثوقة تتحقق من المدخلات.

نكتب اختبارات لقواعد Firestore تشمل: زائر يقرأ منتجًا منشورًا، زائر لا يقرأ الطلبات، مستخدم غير مدير لا يعدل منتجًا، ومدير يستطيع تنفيذ العملية المسموحة فقط.

**مخرج المرحلة:** Firebase Staging محمي وقابل للاختبار، دون بيانات العملاء الحقيقية في البداية.

### المرحلة 5 — استيراد نسخة تجريبية والتحقق

نستورد نسخة من بيانات المصدر إلى Staging فقط، ثم نقارن تقرير ما بعد الاستيراد بتقرير المصدر. نتحقق من عينات يدوية، منها كتاب متوفر، كتاب نفد، كتاب يمكن اقتناؤه، طلب شخصي، طلب هدية، وطلب مختلط.

نحتفظ بالنسخة الأصلية غير المعدلة، ونمنع الاستيراد من الكتابة فوق وثائق موجودة دون سياسة واضحة. أي تعارض في معرف أو حالة يُوقف العملية ويولد تقريرًا بدل التخمين.

**مخرج المرحلة:** تقرير تطابق بيانات مع قائمة اختلافات صفرية أو مبررة وموافق عليها.

### المرحلة 6 — فصل الواجهة عن Flask وربطها بـ Firestore

نحوّل الواجهة الحالية إلى نسخة تعمل من Cloudflare Pages. في هذه المرحلة لا نغيّر الهوية البصرية أو منطق الميزات إلا بالقدر اللازم لاستبدال مصادر البيانات.

التغييرات الرئيسية ستكون:

- استبدال `/api/products` و`/api/categories` و`/api/delivery-fees` بقراءة آمنة من Firestore أو واجهة بيانات مستقرة.
- نقل منطق التحقق الحساس من المتصفح إلى Cloud Functions أو طبقة موثوقة.
- تحويل لوحة الإدارة من `ADMIN_TOKEN` إلى Firebase Authentication وصلاحية مدير.
- إنشاء حالات تحميل وفشل واضحة عند انقطاع Firebase.
- الإبقاء على إدخال رابط الصورة يدويًا، والإبقاء على روابط ImgBB الحالية.
- عدم تمكين أي زر إداري يؤدي إلى حذف نهائي قبل إضافة أرشفة وسجل تغييرات ونسخة احتياطية.

يفضل إصدار واجهات داخلية مستقرة بصيغة `/v1/` إذا استُخدمت Cloud Functions أو Pages Functions، مع مخططات طلب واستجابة واختبارات. عمليات إنشاء الطلبات تحتاج إلى مفتاح idempotency أو معرف جلسة شراء يمنع تكرار الطلب عند إعادة الإرسال.

**مخرج المرحلة:** نسخة Pages Preview متصلة بـ Staging وتحقق تكافؤ الميزات الأساسي.

### المرحلة 7 — الاختبارات الشاملة

ننفذ الاختبارات على طبقات:

| الطبقة | الاختبارات |
|---|---|
| تحويل البيانات | تحويل كل سجل، القيم الناقصة، التكرار، إعادة التشغيل، والتقارير |
| منطق الأعمال | التوفر، السعر، مدة الاقتناء، الهدايا المختلطة، مستلم واحد، وحالات الطلب |
| قواعد Firebase | القراءة العامة، صلاحيات المدير، منع تعديل الأسعار من العميل، وعزل الطلبات |
| الواجهة | البحث، الفلاتر، الاكتشاف، السلة، الشراء، الهدايا، لوحة الإدارة، والوضع الليلي |
| التكامل | إنشاء طلب حقيقي في Staging، منع الطلب المكرر، وفشل الشبكة أو تأخر Firebase |
| النسخ الاحتياطي والرجوع | استعادة مجموعة اختبارية ومقارنة العدادات والبصمات |
| النشر | بناء Pages، معاينة فرع، متغيرات البيئة، وروابط الأصول |

لا ننتقل إلى الإنتاج إذا كانت هناك فروقات غير مبررة في عدد السجلات أو مبالغ الطلبات أو حالات التوفر.

### المرحلة 8 — معاينة المستخدم والتشغيل الموازي

نرسل للمستخدم رابط Pages Preview ورابط لوحة الإدارة التجريبية. يراجع المستخدم المنتجات، صورها، العبارات العربية، مسارات الهدايا، الاكتشاف، والطلبات التجريبية.

يبقى PythonAnywhere مفتوحًا ويستمر مصدر الحقيقة حتى اعتماد النسخة الجديدة. لا يتم إجراء مزامنة تلقائية خطرة بين النظامين؛ أي فرق يظهر أثناء التشغيل الموازي يُسجل ويُعالج بعملية تصحيح واضحة.

**مخرج المرحلة:** موافقة صريحة على الجاهزية للقطع، أو قائمة تعديلات للعودة إلى المرحلة السابقة.

### المرحلة 9 — الترحيل النهائي والقطع

قبل التحويل النهائي نحدد نافذة قصيرة. خلال النافذة:

1. نأخذ تصديرًا نهائيًا من PythonAnywhere.
2. نوقف قبول الطلبات الجديدة مؤقتًا أو نعرض رسالة صيانة قصيرة، حسب ما يوافق عليه المستخدم.
3. نتحقق من أن النسخة النهائية تحتوي كل الطلبات والمنتجات حتى لحظة التجميد.
4. نستورد الفرق فقط إلى Firebase، مع تقرير تطابق.
5. نجري طلبًا تجريبيًا محدودًا ونتحقق من لوحة الإدارة.
6. نربط الدومين أو نعلن رابط Cloudflare Pages الجديد بعد موافقة المستخدم.
7. نبقي PythonAnywhere متاحًا كخطة رجوع، ولا نحذف البيانات القديمة.

لا يتم تغيير DNS أو إيقاف PythonAnywhere تلقائيًا. هذه خطوة تتطلب موافقة صريحة منفصلة لأنها تؤثر في الموقع العام.

### المرحلة 10 — المراقبة وخطة الرجوع

بعد القطع نراقب أخطاء القراءة والكتابة، الطلبات الجديدة، حالات فشل الدفع عند الاستلام، صلاحيات الإدارة، واستهلاك Firebase. إذا ظهر خلل مؤثر، نرجع DNS إلى PythonAnywhere ونوقف استقبال الطلبات من النسخة الجديدة وفق إجراء موثق.

لا نحذف تطبيق Flask أو النسخ الاحتياطية إلا بعد فترة احتفاظ يحددها المستخدم وبعد نجاح اختبار استعادة مستقل. كل طلب جديد أُنشئ في النسخة الجديدة أثناء فترة المراقبة يحتاج إلى سياسة واضحة عند الرجوع حتى لا يُفقد أو يتكرر.

## 5. متطلبات الوصول التي سنحتاجها لاحقًا

لن أطلب أو أضع كلمات المرور في الملفات أو الرسائل. عند الوصول إلى مرحلة التنفيذ سيحتاج المستخدم إلى تنفيذ أو تأكيد خطوات تسجيل الدخول في حساب Cloudflare وFirebase، أو تزويد إعدادات غير سرية فقط. نحتاج أيضًا إلى تصدير `data.json` الحي من PythonAnywhere بطريقة لا تكشفه في المستودع.

الإعدادات العامة مثل Firebase web config يمكن حفظها في إعدادات البناء، لكن صلاحيات المدير ومفاتيح Firebase Admin وImgBB يجب أن تبقى في أسرار البيئة أو في خدمة أسرار مناسبة، لا في JavaScript العام.

## 6. المخاطر وطرق تخفيفها

| الخطر | التخفيف |
|---|---|
| فقدان طلبات بين التصدير والقطع | نافذة تجميد، تصدير نهائي، واستيراد فرق قابل للتكرار |
| تكرار الطلبات | معرفات ثابتة ومفتاح idempotency وفحص قبل الإنشاء |
| عبث العميل بالسعر أو التوفر | إعادة الحساب والتحقق في Cloud Function موثوقة |
| كشف لوحة الإدارة | Firebase Auth، صلاحية مدير، وقواعد Firestore مقيدة |
| اختلاف سلوك حقول قديمة | خريطة تحويل، الاحتفاظ بالحقول الأصلية، واختبارات عينات |
| فشل Firebase أو انقطاع الشبكة | حالات فشل واضحة، عدم تأكيد الطلب حتى نجاح الحفظ، ومراقبة |
| فقدان الصور | إبقاء روابط ImgBB الحالية وعدم حذفها أثناء الجولة الأولى |
| نشر غير مقصود | Pages Preview أولًا، وفرع إنتاج منفصل، وموافقة قبل الربط النهائي |
| فقدان القدرة على الرجوع | إبقاء PythonAnywhere والنسخ الأصلية دون تعديل أو حذف |

## 7. قرارات مطلوبة من المستخدم قبل التنفيذ

1. هل نعتمد **Cloud Firestore** بدل Firebase Realtime Database؟ التوصية: نعم.
2. هل نبقي ImgBB كمخزن الصور في المرحلة الأولى؟ التوصية: نعم، ونرحّل الروابط فقط.
3. هل تريد الإبقاء على الدومين الحالي نفسه عند القطع النهائي؟
4. ما فترة الاحتفاظ التي تريدها للنسخة القديمة بعد نجاح التحويل؟ التوصية: 30 يومًا على الأقل.
5. هل توافق أن إنشاء الطلبات وعمليات الإدارة الحساسة تمر عبر Firebase Cloud Functions بدل الكتابة المباشرة من المتصفح؟ التوصية: نعم.
