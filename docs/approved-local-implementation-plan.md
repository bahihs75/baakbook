# خطة تنفيذ ميزات Baak Books — النسخة المحلية

## الهدف

تنفيذ نظام تجاري متكامل ومحكوم للميزات الجديدة في متجر Baak Books داخل النسخة المحلية الموجودة في `/home/ubuntu/baakbook-local/`، مع الحفاظ على الوظائف الحالية والهوية البصرية العربية التحريرية، ودون تعديل PythonAnywhere أو GitHub أو بيانات العملاء الحقيقية.

سيشمل التنفيذ نظام إهداء متعدد المسارات، زر إهداء مجموعة من السلة، حقول الكتب الجديدة، الكتب التي تُوفَّر عند الطلب، اكتشف كتابك، البحث عن هدية، لوحة الإدارة المحسنة، مفاتيح الميزات، إعادة تصميم بطاقات الكتب، والتعامل الواضح مع الطلبات المركبة.

## القرارات المعتمدة

| القرار | المعتمد |
|---|---|
| مجموعة الهدية في الطلب | مجموعة واحدة فقط |
| عدد المستلمين | مستلم واحد فقط لكل طلب |
| هاتف المستلم | إلزامي لكل هدية |
| الكتب التي تُوفَّر عند الطلب | مسموحة للبيع والإهداء مع إظهار مدة التجهيز |
| مدة الكتاب المتاح للاقتناء | يحددها المدير بخيار مسبق: في اليوم نفسه أو خلال يوم واحد |
| عرض المدة | «يمكن اقتناؤه في اليوم نفسه» أو «يمكن اقتناؤه خلال يوم واحد» |
| الطلب المختلط | يشحن كاملًا بعد اكتمال جميع الكتب |
| تعدد المستلمين | غير متاح في الإصدار الأول؛ يبدأ العميل طلبًا منفصلًا |
| موعد إرسال مستقبلي | غير متاح في الإصدار الأول |
| تغليف الهدية | لا يظهر كخدمة ما لم يكن قابلًا للتنفيذ فعليًا |
| النشر | محلي فقط، مع منع `git push` |

## نطاق الملفات

سيتم فحص وتعديل الملفات المحلية التالية فقط عند الحاجة:

- `app.py`: نماذج البيانات، التحقق من الطلبات، حساب الحالات، واجهات API، إعدادات الميزات، وحفظ الطلبات.
- `store.html`: بطاقات الكتب، الاكتشاف، البحث عن هدية، السلة، زر إهداء المجموعة، نموذج الهدية، وملخص الطلب.
- `admin.html`: نموذج الكتاب، إعدادات الميزات، تصنيف الطلبات، تفاصيل الهدية، وحالات التجهيز.
- `data.json`: بيانات تجريبية محلية فقط، مع إضافة حقول آمنة للمنتجات الحالية دون لمس البيانات الحية.
- `tests/test_app.py`: اختبارات الانحدار واختبارات الرحلات الجديدة.
- `docs/`: توثيق المواصفات وقرارات التصميم وقاموس المصطلحات.

لن يتم تعديل `/home/ubuntu/baakbook/` المنشور، أو ملفات PythonAnywhere، أو مستودع GitHub، ولن يُنفّذ أي دفع إلى remote.

## مراحل التنفيذ

### المرحلة الأولى: تأمين نقطة البداية والتحقق من الوضع الحالي

سيتم إنشاء نسخة محلية إضافية من الملفات التي سيجري تعديلها، ثم فحص حالة Git المحلية والتأكد من أن remote لا يُستخدم للدفع. سيتم تشغيل الاختبارات الحالية قبل التعديل لتثبيت خط أساس واضح، وتسجيل عدد الاختبارات ونتائجها.

سيتم أيضًا التحقق من أن الخادم المحلي يعمل على المنفذ الحالي، وأن `data.json` المستخدم أثناء الاختبار هو ملف البيانات التجريبي المحلي وليس نسخة PythonAnywhere.

### المرحلة الثانية: توسيع نموذج الكتاب بأقل تغيير ممكن

سيُضاف إلى كل منتج نموذج موحد يحافظ على الحقول القديمة ويضع قيمًا افتراضية للحقول الجديدة:

| الحقل | القيمة الافتراضية الآمنة |
|---|---|
| `availability_type` | `in_stock` للكتب القديمة |
| `stock_quantity` | القيمة القديمة إن وجدت، وإلا صفر أو قيمة متوافقة مع البيانات الحالية |
| `lead_time_min_days` | فارغ للكتب المخزونية |
| `lead_time_max_days` | فارغ للكتب المخزونية |
| `giftable` | `false` ما لم يفعّله المدير صراحة |
| `discoverable` | `true` إذا كانت بيانات الاكتشاف كافية، وإلا `false` |
| `discovery_tags` | قوائم فارغة |
| `gift_tags` | قائمة فارغة |
| `active` | يحافظ على القيمة الحالية |

سيُضاف تحقق يحصر مدة الكتاب المتاح للاقتناء في خيارين فقط: في اليوم نفسه أو خلال يوم واحد، ويمنع أن يكون الحد الأدنى أكبر من الحد الأقصى.

### المرحلة الثالثة: بناء منطق التوفر والكتب حسب الطلب

سيتم فصل حالة التوفر عن السعر والكمية. سيحسب الخادم الحالة الحالية من `active` و`availability_type` و`stock_quantity`.

الكتب المخزونية ستقبل فقط كمية لا تتجاوز المتوفر. أما الكتب حسب الطلب فستظهر بشارة ومدة تجهيز، ولن تُعامل كأنها متوفرة فورًا. سيُحفظ في الطلب snapshot للمدة التي كانت معروضة وقت الشراء، حتى لا تتغير الطلبات القديمة إذا عدّل المدير مدة الكتاب لاحقًا.

سيُعتمد في الطلب المختلط حقل تجهيز محسوب بقيمة `mixed`، وحالة تشغيلية تبدأ بـ `awaiting_supply` أو `preparing` بحسب محتوى الطلب، مع سياسة شحن كامل بعد اكتمال جميع العناصر.

### المرحلة الرابعة: توحيد نموذج الإهداء الخلفي

سيُبنى نموذج موحد لمجموعة هدية واحدة داخل الطلب، مع الحقول التالية:

- مصدر الهدية: بطاقة المنتج، مجموعة السلة، أو البحث عن هدية.
- عناصر الهدية وكمياتها.
- اسم المستلم.
- هاتف المستلم الإلزامي.
- طريقة التسليم.
- الولاية والعنوان عند التوصيل المباشر.
- اسم المُهدي، مع خيار إخفائه.
- المناسبة من قائمة مسبقة.
- الرسالة، بحد أقصى 500 حرف.
- إجابات البحث عن الهدية إن كان المسار بدأ من أداة الاقتراح.

سيعيد الخادم حساب السعر والتوفر وقابلية الإهداء من المنتجات الحالية، ولن يثق بالقيم القادمة من المتصفح. وسيمنع أكثر من مجموعة هدية أو أكثر من مستلم في الطلب الواحد.

### المرحلة الخامسة: تنفيذ مسارات الإهداء الثلاثة

#### إهداء كتاب واحد

سيظهر زر «أهدي هذا الكتاب» فقط عند تشغيل نظام الهدايا، وتشغيل مسار بطاقة المنتج، وكون الكتاب قابلًا للإهداء. يضيف الزر الكتاب إلى مجموعة هدية في السلة، ثم يفتح نموذج الهدية الموحد.

#### إهداء مجموعة من السلة

سيُضاف زر «إهداء مجموعة من الكتب» داخل السلة. عند استخدامه، يحدد العميل الكتب القابلة للإهداء، مع إمكانية تحديد الكل. ستنقسم السلة إلى «مشترياتي» و«مجموعة الهدية»، وتبقى مجموعة واحدة ومستلم واحد.

سيتم منع الاختيار الصامت لكتاب غير قابل للإهداء، مع توضيح السبب. وإذا خلط العميل بين كتب شخصية وكتب هدية، سيظهر ملخص منفصل لكل قسم.

#### البحث عن هدية

سيُحافظ على الأسئلة ذات القيم المسبقة، وسيُربط الاختيار بالوسوم الموجودة في المنتجات. ستعرض النتائج حتى ثلاثة اقتراحات مع سبب عربي مفسر. عند اختيار كتاب أو أكثر، ينتقل العميل إلى مجموعة الهدية الموحدة بدل إنشاء منطق Checkout منفصل.

### المرحلة السادسة: تحديث بطاقات الكتب وتجربة المتجر

ستُعاد صياغة البطاقات لتعرض قرارًا واضحًا ومعلومات قليلة مرتبة:

1. الغلاف والعنوان والتصنيف.
2. حالة توفر واحدة.
3. السعر.
4. «أضف إلى السلة» كإجراء أساسي.
5. «أهدي هذا الكتاب» كإجراء ثانوي عند تحقق الشروط.

لن تُعرض شارات متضاربة أو أزرار معطلة بلا سبب. سيُعرض الكتاب حسب الطلب بمدة التجهيز في البطاقة والسلة والمراجعة النهائية للطلب.

سيُراجع الوضع الداكن للتأكد من وضوح النصوص الأساسية، وحالات الخطأ، والشارات، وأزرار الإجراء عالي التباين.

### المرحلة السابعة: تحديث لوحة الإدارة

سيُضاف إلى نموذج الكتاب تقسيم واضح إلى الهوية، البيع والتوفر، الإهداء، والاكتشاف. وسيتم استخدام قوائم القيم المسبقة بدل الكتابة العشوائية للوسوم.

ستعرض لوحة الطلبات:

- نوع الطلب: عادي، هدية، أو مركب.
- نوع التجهيز: مخزون، حسب الطلب، أو مختلط.
- مصدر الهدية.
- المشتريات الشخصية.
- مجموعة الهدية.
- بيانات المستلم والهاتف والعنوان.
- الرسالة والمناسبة واسم المُهدي.
- حالة الطلب وحالة التوفير.

سيُمنع الانتقال العشوائي بين حالات الطلب. وستحفظ الطلبات القديمة حتى عند إيقاف ميزة جديدة.

### المرحلة الثامنة: مفاتيح الميزات والاعتماديات

سيتم توحيد المفاتيح التالية مع الحفاظ على الإعدادات الحالية عند الإمكان:

- `gifts`
- `gift_from_product`
- `gift_from_cart`
- `gift_finder`
- `discovery`
- `on_demand`
- `dark_mode`
- `ideas_lab`

إذا كان `gifts=false`، تتوقف كل مداخل الإهداء ويمنع الخادم طلبات الهدايا الجديدة. أما إيقاف مسار فرعي فيخفي مدخله فقط. لا تحذف عملية الإيقاف المنتجات أو الطلبات السابقة ولا تمسح السلة بصمت.

### المرحلة التاسعة: الاختبارات والترحيل المحلي

سيتم تشغيل اختبار انحدار قبل وبعد كل مجموعة تغييرات. وستُضاف اختبارات تغطي:

1. الطلب العادي القديم.
2. إهداء كتاب واحد من البطاقة.
3. إهداء مجموعة مختارة من السلة.
4. إهداء جميع الكتب القابلة للإهداء.
5. خلط مشتريات شخصية مع مجموعة هدية.
6. رفض كتاب غير قابل للإهداء.
7. كتاب حسب الطلب مع مدة صحيحة.
8. رفض مدة ناقصة أو غير منطقية.
9. هدية حسب الطلب.
10. طلب مختلط يشحن بعد اكتمال جميع الكتب.
11. رقم هاتف مستلم ناقص أو غير صالح.
12. نقص بيانات العنوان عند التوصيل المباشر.
13. تجاوز طول رسالة الهدية.
14. منع مجموعة هدية ثانية أو مستلم ثانٍ.
15. تغير السعر أو التوفر قبل التأكيد.
16. إيقاف مفاتيح الميزات وتأثيره على المداخل والطلبات الجديدة.
17. نتائج «اكتشف كتابك» و«اعثر على هدية» مع سبب منطقي.
18. انتقالات حالات الطلب الصحيحة ورفض الانتقالات غير الصحيحة.
19. إعادة إرسال الطلب دون إنشاء سجل مكرر.
20. وضوح المتجر ولوحة الإدارة في الوضع الداكن.

بعد نجاح الاختبارات، سيُعاد تشغيل الخادم المحلي وتُراجع الرحلات يدويًا عبر رابط المعاينة المحلي.

## تسليمات التنفيذ

عند اكتمال التنفيذ المحلي، سيتم تسليم:

1. رابط المعاينة المحلية.
2. ملخص الملفات المحلية التي تغيرت.
3. عدد الاختبارات الناجحة.
4. جدول بالميزات التي يمكن تشغيلها أو إيقافها من لوحة الإدارة.
5. قائمة بالحالات التي جرى اختبارها.
6. أي قرارات بقيت مؤجلة.

لن يُعتبر العمل جاهزًا للنشر لمجرد نجاح المعاينة. ستكون هناك نقطة مراجعة مستقلة يقرر فيها المستخدم ما يُحتفظ به وما يُحذف، ثم موافقة منفصلة تمامًا قبل أي `git push` أو تحديث PythonAnywhere.

## الافتراضات والمخاطر

| الافتراض أو الخطر | المعالجة |
|---|---|
| `data.json` هو التخزين المحلي الحالي | إضافة حقول متوافقة دون حذف الحقول القديمة |
| لا توجد بوابة دفع ضمن النطاق | الإبقاء على الدفع عند الاستلام وعدم اختراع دورة دفع |
| لا يوجد نظام شحن جزئي | اعتماد الشحن الكامل بعد اكتمال الكتب |
| مدة التوفير تختلف من كتاب لآخر | خيار مسبق لكل كتاب: في اليوم نفسه أو خلال يوم واحد |
| الطلبات القديمة لا تحتوي حقول الميزات | تفسيرها كطلبات قديمة عادية دون كسر عرضها |
| إيقاف ميزة بعد بدء رحلة العميل | إعادة التحقق عند التأكيد وإظهار خيار التحويل أو الإزالة |
| احتمال إدخال بيانات ضارة من المتصفح | تحقق خلفي وإعادة حساب السعر والتوفر |
| تعدد المستلمين قد يزيد التعقيد | منعه في الإصدار الأول وإنشاء طلب مستقل لاحقًا |
| رسائل أو إشعارات خارجية غير متوفرة | عدم عرض وعد بالإرسال الخارجي ضمن الواجهة |
| تغيير كبير في ملفات HTML الحالية | نقاط اختبار بعد كل قسم، مع إمكانية التراجع من النسخة الاحتياطية المحلية |

## ما لن أفعله

لن أعدل النسخة المنشورة على PythonAnywhere، ولن أعدل بيانات العملاء الحقيقية، ولن أرسل أي commit إلى GitHub، ولن أستخدم `git push`، ولن أضيف خدمة خارجية أو خيارًا تجاريًا لا توجد له دورة تشغيل واضحة.

## معيار القبول

تُعد الخطة منفذة بنجاح عندما يستطيع المدير تعريف كتاب متوفر، وكتاب حسب الطلب، وكتاب قابل للإهداء مع وسوم اكتشاف؛ ويستطيع العميل شراء كتاب عادي، إهداء كتاب واحد، إهداء مجموعة مختلطة من السلة، واستخدام البحث عن هدية؛ ويستلم المدير كل طلب ببياناته مفصولة وحالته الصحيحة؛ وتنجح الاختبارات دون تغيير الموقع المنشور.
